# Signalement v1.0 — feuille de route et registre d'interfaces

> **Pour les agents d'exécution :** ce document ne s'exécute pas tâche par tâche. Il
> fixe l'ordre des lots, leurs critères de sortie et les **interfaces partagées entre
> lots**. Chaque lot a son plan détaillé (`2026-10-24-v1-L<n>-*.md`), exécuté avec
> superpowers:subagent-driven-development ou superpowers:executing-plans. Un plan de lot
> qui contredit le registre du §4 a tort : corriger le plan, ou amender ce registre dans
> la même PR, jamais diverger en silence.

**Spec :** `docs/superpowers/specs/2026-10-22-v1-policy-routed-ticket-projection-design.md`
(D1-D13 au §4, critères de sortie au §7, préalables au §8).

**Base :** la tête servie se résout par `git ls-remote --symref origin HEAD` ; ce
document a été écrit sur la base `572b06c` (design fusionné), jamais à reprendre comme
valeur.

## 1. Contraintes globales (valent pour tous les lots)

- Sécurité > qualité > performance > complétude ; TDD strict pour toute logique non
  triviale ; un test ajouté se prouve en le faisant rougir par neutralisation
  (substitution no-op), réponse écrite dans le commit ou la PR.
- `bun run check` vert avant et après chaque commit (`AGENTS.md`). Bun épinglé :
  `packageManager` de `package.json` ; la révision locale se vérifie par
  `bun run check:toolchain`.
- Code et commits en anglais ; DCO par commit (`git commit -s`, identité de la config
  git, sign-off en **dernière ligne**) ; aucun trailer `Co-Authored-By`.
- Aucun chemin absolu machine-local, aucun secret, aucun octet capturé, aucune donnée
  personnelle dans Git ; aucune réponse brute de fournisseur ni jeton en journal.
- Extension : `connect-src 'none'`, `permissions` = `["activeTab", "scripting"]`
  (à partir de L6 seulement), jamais `host_permissions`, `content_scripts`,
  `externally_connectable`.
- Contrats publics canoniques dans `libre-ai/schemas-and-contracts`, vendorisés par
  épinglage dans `vendor/contracts/` ; aucun schéma public redéfini ici.
- Aucune dépendance AGPL/SSPL ; une dépendance nouvelle n'entre que si aucune capacité
  native de Bun, de la WebCrypto ou d'une dépendance déjà installée ne suffit
  (ladder) ; elle est épinglée exactement, âgée d'au moins 3 jours
  (`minimumReleaseAge`), sa licence relevée dans la PR.
- Le texte venu d'une page, d'un Dossier ou d'un fournisseur est une donnée, jamais une
  instruction ; le rendu vers un fournisseur échappe son balisage.
- Une capacité absente est une donnée affichée, jamais un succès simulé.
- Chemins de doctrine (`docs/adr/**`, `project.v1.yaml`, `qualification/**`) :
  artefact de revue requis et ligne `Owner-arbitration:` écrite par le propriétaire,
  jamais par l'agent. Mesure du 2026-10-24 (plan L0) : aucun gate de `signalement` ne
  l'impose (checks requis : « Bun quality » et « licensing » ; aucun ruleset) ; la règle
  tient par convention et par la fusion propriétaire, à rejouer avant de s'y fier.

sur `contract.not_locked:*` jusqu'au verrou. Elle ne fusionne pas dans cet état, et
c'est la seule dérogation à « `bun run check` vert avant chaque commit ».

### 4.1 Contrats publics (L1, `libre-ai/schemas-and-contracts`)

| Id catalogue | Fichier | Rôle |
| --- | --- | --- |
| `signalement-routing-policy-v1` | `contracts/schemas/signalement-routing-policy.v1.schema.json` | version de politique : destinations, règles de routage, refus, divulgation, remise des médias (design §5.3) |
| `signalement-delivery-envelope-v1` | `contracts/schemas/signalement-delivery-envelope.v1.schema.json` | enveloppe de remise : digest et longueur de l'export, origine observée ou `null`, identifiant de remise (design §5.2) |
| `signalement-projection-receipt-v1` | `contracts/schemas/signalement-projection-receipt.v1.schema.json` | reçu signé (design §5.5) |
| `signalement-connector-profile-v1` | `contracts/schemas/signalement-connector-profile.v1.schema.json` | profil exact (design §5.6, `docs/contracts/connector-boundary.md`) |
| `signalement-policy-receipt-v1` | `contracts/wit/signalement-policy-receipt-v1/world.wit` | monde WIT du composant L2 |

Chaque contrat a `SEMANTICS.md` (pour le monde WIT :
`contracts/wit/signalement-policy-receipt-v1/SEMANTICS.md`), des fixtures de schéma
(valides et invalides) et un vérificateur `tools/quality/signalement-<nom>-v1.ts`
exportant `raw<Nom>Failures(bytes: Uint8Array): string[]`, sur le modèle de
`rawLocalExportFailures`. Pour le monde WIT, qui n'a pas de charge utile,
`rawPolicyReceiptFailures` valide le document de vecteurs de référence.

Fixtures publiées par L1, consommées par L2, L3, L5 et L7 :

- `contracts/fixtures/signalement-projection-receipt-v1/signature-vectors.v1.json` —
  corpus de signature, valides et adverses (un tiers doit pouvoir vérifier un reçu) ;
- `contracts/fixtures/signalement-policy-receipt-v1/golden-vectors.v1.json` — vecteurs
  d'évaluation de référence ;
- `contracts/fixtures/signalement-connector-profile-v1/profiles.v1.json` — les 4 profils.

Vendorisation côté `signalement` : `vendor/contracts/pin.json` au format
`signalement.contract-pin.v2` (`contracts[]`, table `files` unique), lu par
`parsePin` / `ContractPin` (`tools/contracts/pin.ts`).

Côté `signalement`, L1 produit aussi le seul module TS de l'enveloppe, consommé par L6
et L7 : `packages/domain/delivery-envelope.ts` exporte `DeliveryEnvelope` (type conforme
au schéma) et `buildDeliveryEnvelope(exportBytes: Uint8Array, observedOrigin: string |
null): Promise<DeliveryEnvelope>`. Le digest d'export est le SHA-256 des octets ZIP
exacts.

Valeurs fixées ici, que les schémas reprennent :

- **Origine observée** : chaîne `scheme://host[:port]` sérialisée par
  `new URL(x).origin` ; schémas admis `https` et `http` ; `null` quand elle est retirée.
- **Identifiant de profil** : `<famille>/<édition>/<api>`, motif
  `^[a-z0-9-]+/[a-z0-9.-]+/[a-z0-9.-]+$`. Valeurs v1.0 :
  `github-issues/github.com/rest-2022-11-28`, `gitlab-issues/gitlab.com/rest-v4`,
  `jira-cloud/cloud/rest-v3`, `plane/self-hosted/rest-v1` (la version exacte de Plane
  est un champ du profil, fixée en qualification).
- **Classes de fichier** : celles de l'export v1, `document`, `screenshot`, `video`
  (`role` du schéma d'export).
- **Décision de divulgation** : `transmit | withhold` ; retenue par défaut.
- **Remise des médias** : `link | withhold` ; défaut `withhold`.
- **Routage** : `imposed`, `optional`, `selectable`, `denied` ; `override: allowed |
  denied`, défaut `denied`.
- **Digests** : SHA-256 en hexadécimal minuscule.
- **Canonicalisation** : JCS (RFC 8785).
- **Signature** : Ed25519, vérification stricte (A et R canoniques, non identité, dans
  le sous-groupe premier ; S canonique). Motif : la vérification Ed25519 native de Bun
  a accepté des falsifications à clé identité (`schemas-and-contracts`,
  `docs/reviews/build-brief-v2-crypto-dependencies.md`).

### 4.2 Composant `policy-receipt` (L2)

Monde WIT `libre-ai:signalement-policy-receipt/api@1.0.0`, octets JSON en entrée et en
sortie, erreurs `contract-error { code: string, message: string }` (modèle :
`ai-model-policy`, `crates/policy-core/src/component.rs`) :

```
evaluate(policy: list<u8>, input: list<u8>) -> result<list<u8>, contract-error>
canonicalize(json: list<u8>) -> result<list<u8>, contract-error>
sign-receipt(unsigned: list<u8>, secret-key: list<u8>) -> result<list<u8>, contract-error>
verify-receipt(signed: list<u8>, public-keys: list<u8>) -> result<list<u8>, contract-error>
```

Côté TS (`packages/policy-receipt-wasm`) :

```ts
export interface PolicyReceiptApi {
  evaluate(policy: RoutingPolicy, input: EvaluationInput): PolicyVerdict;
  canonicalize(value: unknown): Uint8Array;
  signReceipt(unsigned: UnsignedReceipt, secretKey: Uint8Array): SignedReceipt;   // keyId lu dans unsigned.keyId
  verifyReceipt(signed: Uint8Array, publicKeys: PublicKeySet): ReceiptVerification;
}
export function loadPolicyReceipt(): Promise<PolicyReceiptApi>;
```

- `EvaluationInput` = `{ observedOrigin: string | null; files: { path: string; role:
  "document" | "screenshot" | "video"; sha256: string }[]; discovered: Record<string,
  DiscoveredAttributes> }`.
- `PolicyVerdict` = `{ policyVersion: string; policyDigest: string; matchedRuleIds:
  string[]; destinations: VerdictDestination[]; override: "allowed" | "denied";
  deniedCount: number }`, où `VerdictDestination` = `{ destinationId: string;
  profileId: string; routing: "imposed" | "optional" | "selectable"; files: { path:
  string; decision: "transmit" | "withhold"; reason: WithholdReason | null }[]; media:
  "link" | "withhold" }`. Les destinations `selectable` n'apparaissent que si
  `override = "allowed"`. Leur divulgation est calculée par les mêmes règles que les
  autres (design §5.3) : une destination ajoutée par override n'est donc jamais sans
  plan.
- `WithholdReason` = `"default-withhold" | "public-destination" | "residency" |
  "attachment-unsupported" | "visibility-unknown" | "user-withheld"`.
- `ReceiptVerification` = `{ signature: "valid" | "invalid" | "unknown-key" |
  "unreadable"; keyId: string | null; keyStatus: "active" | "retired" | null; receipt:
  ProjectionReceipt | null }` ; `keyId` vaut `null` quand le reçu est illisible ;
  `receipt` n'est non nul que si `signature = "valid"`.
- `ProjectionReceipt` est le contenu d'un `SignedReceipt` dont la signature a été
  vérifiée ; `UnsignedReceipt` est ce même contenu sans signature, `keyId` compris.
- **Précédence des règles (provisoire, question au propriétaire)** : union des règles
  appariées. Un refus domine, l'override le plus restrictif s'applique (contrat L1,
  DL8). L'alternative « règle la plus spécifique » ne changerait que `select_rules` (L2)
  et les vecteurs L1, avant verrou.
- **Visibilité illisible** : tous les fichiers de la destination sont retenus, motif
  `visibility-unknown`. C'est plus strict que « compte comme public » (design §5.5) et
  conforme au test du §7 (« une lecture de visibilité en échec fait retenir »).
- **Organisation** : `verifyReceipt` compare `receipt.organization` à
  `PublicKeySet.organization` ; s'ils diffèrent → `invalid`, raison
  `key.organization_mismatch`.
- `evaluate` ne produit jamais `attachment-unsupported` (capacité du profil) ni
  `user-withheld` (sélection) : ces deux motifs sont posés par `buildDeliveryPlan` (L3).
- `PublicKeySet` = `$defs/signingKeySet` du schéma du reçu (L1, vérifié par
  `rawSigningKeySetFailures`) : `{ organization: string; keys: { keyId: string;
  algorithm: "ed25519"; publicKey: string /* base64url, 32 octets bruts */; status:
  "active" | "retired"; notBefore: string; notAfter: string | null }[] }`, au plus 1024
  clés pour garder vérifiables les reçus signés par des clés retirées. C'est exactement
  le `data` de `GET /api/v1/signing-keys`.
- `secretKey` de `signReceipt` = graine Ed25519 de 32 octets.
- `DiscoveredAttributes` = `{ visibility: "public" | "internal" | "private" |
  "unknown"; attachmentUpload: boolean }` ; la résidence est déclarée dans la politique,
  jamais découverte.
- `ProjectionReceipt` : forme fixée par le schéma `signalement-projection-receipt-v1`
  (L1), type TS généré ou recopié par L2 sans le redéfinir. Outre les champs minimaux
  du design §5.5, il porte `rendered` = `{ rendererVersion: string; bodyDigest: string;
  mediaLinks: { path: string; url: string }[] }`. `bodyDigest` est le SHA-256 du **JCS**
  de `RenderedBody.body` (un objet `RenderedContent`), distinct de `requestBodyDigests`
  (requêtes HTTP entières). Le reçu porte aussi `revision` (révision du Dossier livrée) :
  avec le document de l'export, `projectionId`, `revision` et `mediaLinks`, il suffit à
  recalculer le rendu hors ligne (`RenderInput`, §4.4), pour une création comme pour un
  commentaire.
- `rendererVersion` est un semver (`1.0.0`), par profil, dans `RENDERER_VERSIONS` (L3)
  comme dans le schéma L1 ; le reçu porte `profileId`, qui identifie le moteur.
- La CLI et le control plane chargent **le même** artefact WASM ; la clé secrète ne
  sort jamais du control plane. Le chargeur (L2) doit fonctionner aussi dans un
  exécutable `bun build --compile` : glue et module embarqués (import de fichier), pas
  d'`import()` dynamique d'un chemin `target/…` ; un test de L2 le prouve.

### 4.3 `packages/connector-sdk` (L3, Apache-2.0)

```ts
export type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };
export interface ConnectorFailure {
  kind: "auth" | "not-found" | "rate-limited" | "conflict" | "unsupported"
      | "invalid-mapping" | "ambiguous" | "transport" | "provider-error";
  retryable: boolean;
  retryAfterMs: number | null;
  code: string;            // stable, machine-readable, never a raw provider body
}
export interface HttpPort { send(request: OutboundRequest): Promise<OutboundResponse>; }
export interface Connector {
  readonly profiles: readonly ConnectorProfile[];
  discover(target: DestinationTarget, ctx: ConnectorContext): Promise<Result<Discovery, ConnectorFailure>>;
  validateMapping(target: DestinationTarget, ctx: ConnectorContext): Promise<Result<MappingReport, ConnectorFailure>>;
  findByMarker(target: DestinationTarget, marker: ProjectionMarker, ctx: ConnectorContext): Promise<Result<FindOutcome, ConnectorFailure>>;
  create(request: CreateRequest, ctx: ConnectorContext): Promise<Result<RemoteItemReceipt, ConnectorFailure>>;
  comment(request: CommentRequest, ctx: ConnectorContext): Promise<Result<RemoteItemReceipt, ConnectorFailure>>;
  attach(request: AttachRequest, ctx: ConnectorContext): Promise<Result<AttachmentReceipt, ConnectorFailure>>;
  readChanges(target: DestinationTarget, cursor: string | null, ctx: ConnectorContext): Promise<Result<ChangePage, ConnectorFailure>>;
}
```

- `ConnectorContext` = `{ http: HttpPort; credential: SecretHandle; clock: () => string }`.
- `FindOutcome` = `{ consistency: "strong"; item: RemoteItemRef | null } |
  { consistency: "unavailable" }` ; `"unavailable"` mène à `to-resolve`, jamais à une
  création.
- `RemoteItemReceipt` = `{ remoteId: string; remoteUrl: string; requestBodyDigests:
  string[] }` ; les digests sont ceux des corps réellement envoyés, calculés par le
  `HttpPort` instrumenté, pas par le connecteur.
- `SecretHandle` ne s'imprime pas (`toString`, `toJSON` et l'inspection renvoient
  `"[secret]"`) ; `SecretHandle.fromString(value)` le construit, `revealSecret(handle)`
  est le seul accès à la valeur.
- `ProjectionMarker` porte `notBefore: string` (ISO 8601, heure de la première
  tentative) : la reprise par liste ne remonte pas avant cette date. Elle voyage dans
  `DeliveryJob.firstAttemptAt`, alimenté par la colonne `deliveries.first_attempt_at`
  (L4).
- Accesseurs de profil, seuls moyens de lire les capacités (les noms de champs suivent
  le schéma L1) : `profileIdOf(profile)`, `attachmentModeOf(profile)`,
  `lookupOf(profile)`.
- Transport réel : `createFetchHttpPort(options: { timeoutMs: number; maxResponseBytes:
  number; allowPrivate: boolean }): HttpPort` vit dans le SDK (L3), pas dans
  `apps/control-plane`, parce que L4 et l'outillage de qualification de L5 le consomment
  tous deux. `allowPrivate: false` refuse les adresses privées, de bouclage et
  lien-local (garde SSRF) ; seule une destination Plane auto-hébergée déclarée sur un
  réseau privé le met à `true`, par configuration d'administrateur journalisée.

### 4.4 `packages/projection-core` (L3)

```ts
export type ProjectionState = "pending" | "dispatching" | "created" | "updated" | "to-resolve" | "failed";
export function projectionId(organization: string, dossierId: string, destinationId: string): string;
export function idempotencyKey(projectionId: string, exportDigest: string, mappingVersion: string): string;
export function buildDeliveryPlan(verdict: PolicyVerdict, selection: UserSelection, profileFor: (profileId: string) => ConnectorProfile | null): DeliveryPlan;
// profileFor : profil qualifié servi (L4 le dérive de connectorFor + matrice) ; null → destination refusée,
// jamais une fixture figée lue par projection-core.
export function revalidatePlan(plan: DeliveryPlan, current: RevalidationInput): "send" | "to-resolve";
export function transition(state: ProjectionState, event: ProjectionEvent): ProjectionState;
export function renderBody(profileId: string, input: RenderInput): RenderedBody;   // { rendererVersion, body, marker }
export function executeDelivery(job: DeliveryJob, deps: DeliveryDeps): Promise<DeliveryOutcome>;
export function buildUnsignedReceipt(job: DeliveryJob, outcome: DeliverySuccess, signing: { keyId: string; issuedAt: string }): UnsignedReceipt;
```

- `executeDelivery` est l'algorithme d'une livraison, partagé par le dispatcher (L4) et
  la suite de conformité (L5) : revalidation (`revalidatePlan`), puis, si une tentative
  précédente est ambiguë, `findByMarker` (`unavailable` → `to-resolve`), puis `create`
  (première livraison) ou `comment` (révision), puis `attach` ou repli déclaré.
  `DeliveryDeps` = `{ connector: Connector; ctx: ConnectorContext; readFile(path:
  string): Promise<Uint8Array>; rediscover(): Promise<Result<Discovery,
  ConnectorFailure>> }`. Aucune I/O hors de `deps`.
- `DeliveryOutcome` = `{ kind: "success"; value: DeliverySuccess } | { kind:
  "to-resolve"; reason: string } | { kind: "retry"; failure: ConnectorFailure } |
  { kind: "failed"; failure: ConnectorFailure }`.

- `idempotencyKey` = SHA-256 hexadécimal du JCS de
  `[projectionId, exportDigest, mappingVersion]` ; `projectionId` = SHA-256
  hexadécimal du JCS de `[organization, dossierId, destinationId]`.
- `UserSelection` ne peut que **retirer** : destinations optionnelles cochées, ajouts
  pris dans `selectable` si `override = "allowed"`, fichiers retenus en plus. Toute
  sélection qui ajouterait un `transmit` est rejetée (`selection.escalation`).
- Libellés d'écran (design §5.4) : `created` → « créé », `updated` → « mis à jour »,
  `pending`/`dispatching` → « en attente », `to-resolve` → « à résoudre »,
  `failed` → « échec ».

Faux fournisseur (L3, `packages/fake-provider`), consommé par L4, L5, L6 et L7 :
`createFakeProvider(options: { dialect; search; baseUrl }): FakeProvider` (options du
plan L3 ; dialectes par famille exportés par L5 via `fakeDialectFor(profileId: string):
FakeDialect | null`, `connectors/conformance/dialects/index.ts`) (un `HttpPort` qui capture chaque requête et
injecte des pannes) et `findLeaks(captured, withheld): Leak[]`, l'instrument du
prédicat `destination-disclosure-leak`. Port instrumenté (SDK) :
`instrumentHttpPort(port: HttpPort): InstrumentedHttpPort`.

### 4.4 bis Connecteurs (L5)

Chaque famille exporte depuis `connectors/<famille>/index.ts` un `Connector` et ses
`ConnectorProfile` exacts ; `connectors/index.ts` exporte
`connectorFor(profileId: string): Connector | null` et `CONNECTORS: readonly Connector[]`,
seuls points d'entrée consommés par L4 (pas de `installedConnectors` ni de
`ConnectorRegistry` concurrent). Un `profileId` absent ou non `qualified` rend `null` côté L4 ; la suite
de conformité (`connectors/conformance`) exerce les connecteurs par `executeDelivery`.

### 4.5 Control plane (L4), API `/api/v1`

Enveloppe `{ data, meta }`, pagination par curseur (`meta.nextCursor`), erreurs
`{ error: { code, message } }` sans donnée fournisseur brute.

| Méthode et chemin | Rôle | Consommé par |
| --- | --- | --- |
| `POST /api/v1/deliveries/uploads` | reçoit l'export + l'enveloppe ; revérifie ; crée ou révise le Dossier | L6 (page), L7 (`submit`) |
| `GET /api/v1/dossiers/{id}` | Dossier, révisions, N états de projection, identifiants de reçus | L4 web, L7 (`status`) |
| `GET /api/v1/dossiers/{id}/plan` | verdict + plan par destination pour l'écran d'envoi | L4 web |
| `POST /api/v1/dossiers/{id}/approvals` | approbation par destination, liée au plan exact | L4 web |
| `GET /api/v1/receipts/{id}` | reçu signé (octets JCS, `application/json`) | L7 (`receipt`) |
| `GET /api/v1/signing-keys` | `PublicKeySet` (§4.2), clés actives et retirées | L7 (`keys`) |
| `GET /api/v1/profiles` | profils `qualified` seulement | L4 web |
| `POST /api/v1/tokens` | émission de jeton Biscuit atténué pour la CLI, depuis la session web | L4 web |
| `GET /artifacts/{artifactId}` | média servi aux seuls membres authentifiés ; cible des `mediaLinks` (remise `link`), donc URL écrite dans les tickets | fournisseurs (via lien), L4 web |

Le tableau ne liste que les routes partagées entre lots. Les routes internes de L4
(`/api/v1/admin/**`, `/auth/**`, `/healthz`…) vivent dans son plan.

`POST /api/v1/deliveries/uploads` : corps `application/zip` = octets exacts de l'export,
lus par flux borné ; enveloppe `signalement-delivery-envelope-v1` en JCS, encodée
base64url dans l'en-tête `Signalement-Delivery-Envelope` (4096 octets au plus). Réponse
`201` avec `data` = `{ dossierId: string; revisionId: string; exportSha256: string;
created: boolean }`. Le même export remis deux fois rend `200` avec la révision
existante et `created: false` (design §5.5). *Choix de la feuille de route : un corps
brut se lit par flux borné ; un multipart de 256 Mio se charge en mémoire.*

Authentification : cookie de session `__Host-` (OIDC) pour le web ; pour la CLI, en-tête
`Authorization`, schéma `Bearer`, valeur = jeton Biscuit. Toute table d'organisation
porte `organization` et une politique RLS ; le rôle applicatif n'a pas `BYPASSRLS`.

Banc de test produit par L4 et consommé par L6 et L7 :
`apps/control-plane/testing/harness.ts` exporte
`startTestControlPlane(options?: { profiles?: string[] }): Promise<TestControlPlane>`,
avec `TestControlPlane` = `{ url: string; issueToken(role: "reporter" | "policy-admin" |
"auditor"): Promise<string>; approveAll(dossierId: string): Promise<void>;
drainOutbox(): Promise<void>; fakeProvider: FakeProvider; stop(): Promise<void> }`. Base
PostgreSQL de test et `packages/fake-provider` (L3) derrière.

Point d'accroche de la page de réception, produit par L4 et consommé par L6 :
`ReceiverHost` (dont `upload(exportBytes, envelope)`, qui appelle la route ci-dessus) et
`MountReceiver`, définis par le plan L4. L6 fournit `mountReceiver` et le récepteur.

Vérification de l'export : la page vérifie le **transport** (longueur, SHA-256 annoncé,
archive lisible par `readZip`, présence de `manifest.json`). Le verdict de conformité
`verifyExport` est rendu par le serveur et affiché par la page. Motif : le vérificateur
vendorisé ne tourne pas en navigateur (`node:crypto`, `Bun.file` au chargement, Ajv
compilé à l'exécution qui exigerait `unsafe-eval`). C'est un écart au design §5.2 point 5,
soumis au propriétaire.

Matrice de qualification : `tools/ci/qualification.ts` n'admet aujourd'hui que
`verified | assumed | rejected | unresolved`. L5 l'étend au statut `qualified` et à un
champ `profile` (identifiant exact du §4.1) ; L4 lit `status: qualified` et `profile`.

### 4.6 Remise (L6) — protocole par morceaux

Message `postMessage` vers l'origine configurée **exacte**, monde isolé, fonction
injectée fixe :

```ts
type DeliveryMessage =
  | { type: "signalement.delivery.begin"; deliveryId: string; envelope: DeliveryEnvelope; chunkCount: number }
  | { type: "signalement.delivery.chunk"; deliveryId: string; index: number; bytes: string /* base64 */ }
  | { type: "signalement.delivery.end"; deliveryId: string };
type DeliveryAck = { type: "signalement.delivery.ack"; deliveryId: string; index: number | "begin" | "end"; ok: boolean; code: string | null };
```

La taille de morceau est fixée par L6 après mesure ; le digest annoncé dans
l'enveloppe est vérifié par la page avant téléversement, puis par le serveur.

`packages/delivery-protocol` (L6) exporte les constantes (`DELIVERY_CHUNK_BYTES`,
`DELIVERY_CHUNK_BYTES_CEILING`, `MAX_DELIVERY_CHUNKS`, délais), `deliveryMessages`
(découpage), `createReassembler` (réassemblage borné), `parseDeliveryMessage`,
`parseDeliveryAck`, et l'ensemble fermé `DeliveryAckCode`, qui type `DeliveryAck.code`
(`DeliveryAckCode | null`). Il **ne construit pas** l'enveloppe : il importe
`DeliveryEnvelope` et `buildDeliveryEnvelope` de `packages/domain/delivery-envelope.ts`
(L1). Champs de l'enveloppe, à reprendre du schéma L1 : `deliveryId` (UUID v4 en minuscules,
`crypto.randomUUID()`), `exportSha256`, `exportByteLength`, `observedOrigin`.

### 4.7 CLI (L7)

```
signalement submit <export.zip> (--origin <origin> | --no-origin) [--server <url>]
signalement status <dossier-id> [--server <url>]
signalement receipt <receipt-id> [--server <url>]     # écrit le reçu JCS sur stdout
signalement keys [--server <url>]                     # écrit le PublicKeySet sur stdout
signalement verify-receipt <receipt.json> --keys <keys.json> [--export <export.zip>]
```

`receipt` et `keys` téléchargent seulement ; `verify-receipt` ne touche jamais le
réseau. L'ancre de confiance des clés (fichier servi par le serveur qui signe, ou
canal hors bande) est une question ouverte au propriétaire.

Jeton depuis `SIGNALEMENT_TOKEN`, serveur depuis `--server` ou `SIGNALEMENT_SERVER`.
Codes de sortie : `0` vérifié ou accepté, `1` refusé ou invalide, `2` usage. Sortie
JSON sur stdout ; jamais le jeton.
