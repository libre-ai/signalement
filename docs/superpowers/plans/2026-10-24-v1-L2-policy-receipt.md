# Signalement v1.0 — L2 policy-receipt (Rust → WASM) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** livrer `crates/policy-receipt` (évaluation de politique pure et déterministe, canonicalisation JCS, signature et vérification Ed25519 strictes des reçus), compilée en un composant WASM sans capacité, construit de façon reproductible et jamais commité, plus `packages/policy-receipt-wasm`, le chargeur TypeScript que le control plane (L4) et la CLI (L7) instancient à l'identique.

**Architecture:** une crate Rust `cdylib + rlib` expose quatre fonctions octets JSON → octets JSON (`evaluate`, `canonicalize`, `sign_receipt`, `verify_receipt`). Le monde WIT `signalement-policy-receipt` (interface `libre-ai:signalement-policy-receipt/api@1.0.0`), rédigé par L1 et vendorisé sous `vendor/contracts/`, est exporté par un module `component` compilé seulement pour `wasm32`. La chaîne reprend celle de `libre-ai/ai-model-policy` (`tools/quality/build-policy-core-wasm.ts`) : `cargo build --target wasm32-unknown-unknown --release` avec remappage des chemins machine, `componentNew` puis `componentWit`, `transpileBytes` de jco en instanciation asynchrone, contrôle « zéro import » côté Rust (`examples/check_wasm_imports.rs`) et côté hôte, balayage des chemins machine, manifeste. Le chargeur TS instancie la glue générée avec un objet d'imports vide et traduit les `contract-error` en `PolicyReceiptError`.

**Tech Stack:** Rust (version de la flotte : `gh api repos/libre-ai/ai-model-policy/contents/rust-toolchain.toml --jq .content | base64 -d`), cible `wasm32-unknown-unknown`, `wit-bindgen`, `serde`, `serde_json`, `serde_jcs`, `sha2`, `ed25519-dalek`, `curve25519-dalek`, `base64`, `zeroize` ; Bun (épinglé par `packageManager`), TypeScript strict, `@bytecodealliance/jco-transpile`, `ajv` (déjà installé), `bun:test`.

**Spec:** docs/superpowers/specs/2026-10-22-v1-policy-routed-ticket-projection-design.md ; feuille de route docs/superpowers/plans/2026-10-24-v1-roadmap.md

## Global Constraints

- **Ordre (feuille de route §2).** L2 développe sur une branche qui vendorise les contrats L1 au statut `candidate` (L1 Task 11). Cette branche est rouge par construction sur `contract.not_locked:*` jusqu'au verrou ; c'est la seule dérogation admise à « `bun run check` vert avant chaque commit ». Elle ne fusionne qu'après le passage des contrats en `locked` et le ré-épinglage sur `main` (Task 15).
- **Gate de branche L2 (avant le verrou).** À la place de `bun run check` à chaque commit :
  ```bash
  for s in $(jq -r '.scripts["check:tree"]' package.json | grep -oE 'bun run [a-z:-]+' | awk '{print $3}' | grep -vx check:contracts); do bun run "$s" || { echo "FAIL $s"; break; }; done
  bun run check:contracts 2>&1 | grep -E '^[a-z]+\.[a-z_]+'   # attendu : uniquement des lignes contract.not_locked:signalement-*
  bun run check:development-history
  ```
  Après le verrou (Task 15), `bun run check` seul fait foi.
- **Contrats.** Les noms du registre §4.1 et §4.2 sont repris tels quels. La syntaxe JSON et la sémantique d'évaluation sont celles de L1 (`SEMANTICS.md` des contrats vendorisés ; plan L1 part-1, Task 4 et Task 5). Si le contrat vendorisé diffère d'un nom écrit ici, le contrat gagne, le test suit le contrat, l'écart est signalé dans la PR.
- **Aucune I/O dans la crate.** Ni horloge, ni aléa, ni réseau, ni fichier, ni environnement. Le composant n'importe rien : vérifié par `check_wasm_imports`, par la construction et par le chargeur.
- **Pas de panique.** `lib.rs` porte `#![deny(unsafe_code, clippy::unwrap_used, clippy::expect_used, clippy::panic)]` ; seul `component.rs` porte `#[allow(unsafe_code)]` (code généré par `wit-bindgen`, comme le précédent) ; les modules de test portent `#[allow(clippy::unwrap_used, clippy::expect_used)]`.
- **Messages d'erreur.** `contract-error.message` est une phrase anglaise fixe par code ; elle ne cite jamais un octet d'entrée.
- **Clé secrète.** Générée côté hôte (WebCrypto, L4) ; la crate signe et vérifie seulement. La graine est copiée dans un `Zeroizing<[u8; 32]>`, le `Vec<u8>` reçu par le composant est effacé par `zeroize` avant retour ; rien ne renvoie ni ne journalise de matériel secret. La CLI ne signe rien (D11).
- **Dépendances Rust.** Versions exactes dans `[workspace.dependencies]`, `Cargo.lock` commité, `cargo … --locked`. Reprises de `ai-model-policy/Cargo.toml` : `serde`, `serde_json`, `serde_jcs`, `sha2`, `wit-bindgen`, `wasmparser`, `wit-component`. Crypto : `ed25519-dalek =2.2.0`, `curve25519-dalek =4.1.3` (BSD-3-Clause), versions de `schemas-and-contracts` `docs/reviews/build-brief-v2-crypto-dependencies.md`. `base64 =0.22.1` (MIT OR Apache-2.0, même source). `zeroize` à la version déjà résolue par `ed25519-dalek`. Pas de crate de tests de propriété : générateur borné écrit en Task 7.
- **Dépendance TS nouvelle.** `@bytecodealliance/jco-transpile` `0.4.2` exact (`Apache-2.0 WITH LLVM-exception`, publiée le 2026-07-09), version de `ai-model-policy`. Motif : aucune capacité de Bun ne convertit un module cœur en composant ni ne transpile un composant. Licences transitives (`binaryen`, `oxc-minify`, `@bytecodealliance/preview2-shim`, `@bytecodealliance/preview3-shim`) relevées dans la PR : **à vérifier à l'exécution**.
- **Artefact non commité.** Tout produit vit sous `target/` (déjà dans `.gitignore`).
- **Preuve.** Chaque test ajouté se prouve par une substitution no-op décrite à l'étape « Neutralisation », rappelée dans le commit. Stager avant les gates qui parcourent l'arbre.
- **Commits.** Anglais, `git commit -s`, sign-off en dernière ligne, aucun `Co-Authored-By`, aucune ligne `Owner-arbitration:`.
- **Chemins et faits volatils.** Aucun chemin absolu machine-local suivi ; les tests Rust résolvent les vecteurs depuis `env!("CARGO_MANIFEST_DIR")` et le catalogue vendorisé. Version Rust, sha de gouvernance, nom du monde, version de `zeroize` : résolus par commande, jamais recopiés.

### Contrat consommé (résumé, source : plan L1 part-1 Task 4 et 5, registre §4.2)

- **Politique** : `{ schemaVersion: "libre-ai.signalement-routing-policy.v1", organization, policyId, version, destinations, routingRules, disclosureRules }`. Destination `{ id, profileId, target, residency: "eu"|"non-eu", visibilitySource: "discovered"|"declared", declaredVisibility?, mediaFallback? }`. Règle de routage `{ id, match, imposed, optional, selectable, denied, override? }`, `match` ∈ `{ origin }` | `{ scheme, hostPattern, port }` | `{ absent: true }`. Règle de divulgation `{ id, roles, when, decision }`, `when` ∈ `{ always: true }` | `{ visibility }` | `{ residency }`. Bornes : destinations 1..64, règles 0..256, listes 0..64, `roles` 1..3, 1 MiB. `hostPattern` : `^\*\.(?:[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z]{2,63}$`, tout sous-domaine à toute profondeur, jamais l'apex ; `port: null` = origine sans port.
- **Évaluation (DL8 de L1)** : appariement (origine égale octet pour octet ; ou schéma, motif, port ; ou `absent` si `observedOrigin === null`) ; combinaison des règles retenues : `denied` = union, `imposed` = union − `denied`, `optional` = union − `imposed` − `denied`, `selectable` = union − les trois ; `deniedCount` = |`denied`| ; `override` = `allowed` seulement si au moins une règle retenue et toutes `allowed`. Destinations du verdict : `imposed`, `optional`, et `selectable` seulement si `override = "allowed"`, triées par `destinationId`. Visibilité effective : `declaredVisibility` si `declared`, sinon `discovered[id].visibility` (entrée absente = `unknown`), `internal` vaut `public`. Décision par fichier (triés par `path`) : `unknown` → `withhold`, `visibility-unknown` ; règle `withhold` applicable → `withhold`, motif de la première dans l'ordre du document (`visibility` → `public-destination`, `residency` → `residency`, `always` → `default-withhold`) ; aucune règle `transmit` → `withhold`, `default-withhold` ; sinon `transmit`. `evaluate` ne lit pas `attachmentUpload` et ne produit jamais `attachment-unsupported` ni `user-withheld` (L3). `policyVersion` = `version` ; `policyDigest` = SHA-256 de JCS(document). Règles retenues = toutes les règles appariées, dans l'ordre du document (`select_rules`, Review Focus 1).
- **Reçu** (plat, ASCII, sans nombre JSON) : `UnsignedReceipt` = `{ schemaVersion, organization, keyId, issuedAt, deliveredAt, exportDigest, projectionId, revision, mappingVersion, operation, destinationId, profileId, remote, transmitted, withheld, rendered: { rendererVersion, bodyDigest, mediaLinks }, requestBodyDigests, policy, approval }` (`revision` = révision du Dossier livrée ; motif de `rendererVersion` : celui du schéma L1 vendorisé, jamais recopié ici — le registre §4.2 dit semver, la coordination du 2026-10-24 `^[a-z0-9-]+\.[1-9][0-9]*$`, contradiction signalée) ; `SignedReceipt` = idem + `signature: { algorithm: "ed25519", value }` (base64url, 86 caractères). Message signé : UTF-8 `libre-ai.signalement-projection-receipt.v1` ‖ `0x00` ‖ SHA-256(JCS(reçu sans `signature`)) en 32 octets bruts. Document signé exigé sous forme JCS.
- **`PublicKeySet`** (registre §4.2) : `{ organization, keys: [1..1024] { keyId, algorithm: "ed25519", publicKey (base64url, 43 caractères, 32 octets), status: "active"|"retired", notBefore, notAfter } }` ; une clé vérifie les reçus dont `issuedAt` ∈ [`notBefore`, `notAfter`).
- **Vérification** (L1 part-2, Task 6, ordre normatif) : reçu refusé par `rawProjectionReceiptFailures` ou `signature.value` non canonique → `unreadable` ; jeu de clés refusé → erreur `keys.invalid` ; `receipt.organization` ≠ `PublicKeySet.organization` → `invalid`, `keyStatus: null` (raison L1 `key.organization_mismatch`, avant toute recherche de clé) ; `keyId` absent → `unknown-key` ; hors fenêtre → `invalid` ; A non admissible, R non admissible, S ≥ L, puis `verify_strict` faux → `invalid` ; sinon `valid`. `keyStatus` = statut de la clé dès qu'elle est trouvée ; `keyId` = celui du reçu pour tout verdict autre que `unreadable`.
- **Vecteurs de référence** : `golden-vectors.v1.json`, `cases: [{ id, operation, args, expected: { ok } | { error: { code } }, rationale }]` pour les quatre opérations ; arguments JSON (`policy`, `input`, `unsigned`, `publicKeys`, `json`) ou base64url (`secretKey`, `signed`, `jsonBytes`). Corpus de signature : `signature-vectors.v1.json`, 32 `vectors` dans la table L1 (dont `keyset-other-organization`) (`expected` = `{ signature, keyStatus, reason }` ou `{ refused }`) et des `signCases` (`seed`, `unsigned`, `signed` exact).
- **`DiscoveredAttributes`** : `{ visibility: "public"|"internal"|"private"|"unknown"; attachmentUpload: boolean }`.
- **Horodatages** : `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$` (export v1) ; la comparaison lexicale est exacte sur cette forme.

### Codes d'erreur (`contract-error.code`, `SEMANTICS.md` du monde WIT)

| Fonction | Codes |
| --- | --- |
| `evaluate` | `input.too_large`, `policy.invalid`, `input.invalid`, `input.origin_invalid` |
| `canonicalize` | `canonicalize.too_large`, `canonicalize.raw_json` (dont membre dupliqué, BOM, octets en trop), `canonicalize.number` (tout flottant, tout entier hors ±(2⁵³ − 1)), `canonicalize.lone_surrogate`, `canonicalize.depth` (> 64) |
| `sign-receipt` | `receipt.invalid`, `key.invalid` (graine ≠ 32 octets) |
| `verify-receipt` | `keys.invalid` (jeu de clés refusé par l'un des contrôles de `rawSigningKeySetFailures` : taille 262 144, JSON strict, schéma, `keyId` dupliqué, `retired` sans `notAfter`, fenêtre inversée, base64url non canonique) |
| toutes | `internal.error` (sérialisation interne ; attendu jamais, présent pour qu'aucun chemin ne panique) |

Un reçu illisible n'est pas une erreur : `verify-receipt` rend `{ signature: "unreadable", keyId: null, keyStatus: null, receipt: null }` (registre §4.2). Bornes : politique, entrée, `canonicalize` ≤ 1 048 576 octets ; `unsigned` et `signed` ≤ 65 536 ; `public-keys` ≤ 262 144 ; profondeur ≤ 64 ; `files` ≤ 33, `path` ≤ 80 octets (export v1).

## Review Focus

1. **Précédence des règles (défaut provisoire, décision propriétaire attendue).** Défaut = **union** des règles appariées (DL8 de L1 : un refus domine, l'`override` le plus restrictif s'applique), arbitrage de l'orchestrateur du 2026-10-24 pour la cohérence des plans. Le choix vit dans une seule fonction, `select_rules`, testée par `select_rules_table` (Task 5) ; `combine` applique ensuite l'union. Alternative « règle la plus spécifique » : elle changerait le corps de `select_rules` et sa table, plus les vecteurs L1 `denied-dominates` et `override-most-restrictive`, avant le verrou.
2. **Origine observée non normalisée.** `https://Example.test`, `https://example.test:443`, `https://example.test.`, `https://example.test/` → `input.origin_invalid`, jamais un appariement. Test : `observed_origin_must_be_serialized_form` (Task 4).
3. **Confusion de suffixe du motif.** `*.example.test` (schéma `https`, port `null`) apparie `https://a.example.test` et `https://a.b.example.test`, jamais `https://example.test`, `https://evilexample.test`, `https://a.example.test.evil.test`, `http://a.example.test`, `https://a.example.test:8443`. Test : `host_pattern_matches_subdomains_same_scheme_and_port` (Task 5).
4. **Visibilité inconnue.** Entrée `discovered` absente ou `unknown` sur une destination `discovered` → tous ses fichiers `withhold`, `visibility-unknown`, même avec une règle `transmit always` ; `internal` → `public-destination` si une règle retient le public. Test : `unknown_visibility_withholds_every_file` (Task 6).
5. **Collision et fenêtre de clé.** Reçu signé par la clé A, jeu où `keyId` A porte la clé B → `invalid`, `keyStatus` de l'entrée, jamais `valid` ; `issuedAt` égal à `notAfter` (borne exclue) ou antérieur à `notBefore` → `invalid` ; `keyId` dupliqué → `keys.invalid` ; reçu d'une organisation vérifié contre le jeu d'une autre → `invalid`. Tests : `wrong_key_for_key_id_is_invalid`, `key_window_is_half_open`, `organization_mismatch_is_invalid` (Task 9).
