# Signalement v1.0 — L7 CLI cliente et vérificateur hors ligne Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** livrer `apps/cli`, une CLI qui envoie un export local vérifié au control plane
(`submit`), affiche les N états de projection d'un Dossier (`status`), télécharge un reçu
signé et le jeu de clés publiques (`receipt`, `keys`), et vérifie un reçu entièrement hors
ligne (`verify-receipt`), avec les commandes, l'environnement et les codes de sortie
exacts du registre §4.7, et le critère `signed-receipt-offline` vert sans réseau.

**Architecture:** un point d'entrée mince (`apps/cli/main.ts`) délègue à
`run(argv, env, deps)`, dont toutes les I/O sont injectées (lecture de fichier bornée,
HTTP, chargement du composant WASM). Chaque commande vit dans son module et rend un
`CliResult` : soit un rapport JSON, soit, pour `receipt` et `keys`, les octets JCS
téléchargés. La lecture d'export réutilise la borne et le vérificateur de
`tools/contracts/verify-export.ts` ; l'enveloppe vient de
`packages/domain/delivery-envelope.ts` (L1) ; la vérification de reçu consomme
`loadPolicyReceipt()` (L2) ; le recalcul du rendu consomme `parseExportPayloadView`,
`buildRenderInput`, `renderBody` et `RENDERER_VERSIONS` (L3). Le seul module qui lit les
noms de champs du reçu est l'adaptateur `receiptFacts`. Le client HTTP enrobe `fetch` et
échoue fermé (TLS strict, aucune redirection suivie, corps de réponse borné, délais). Un
garde refuse d'imprimer toute sortie contenant le jeton.

**Tech Stack:** TypeScript strict, Bun (version épinglée par `packageManager` de
`package.json`, vérifiée par `bun run check:toolchain`), `fetch`, `node:util` `parseArgs`,
`node:crypto` (SHA-256), `bun build --compile` ; `packages/policy-receipt-wasm` (L2) ;
`packages/projection-core` (L3) ; `apps/control-plane/testing/harness.ts` (L4, tests de
bout en bout). Aucune dépendance nouvelle.

**Spec:** docs/superpowers/specs/2026-10-22-v1-policy-routed-ticket-projection-design.md ; feuille de route docs/superpowers/plans/2026-10-24-v1-roadmap.md

## Global Constraints

- **Préalables.** L2 et L4 fusionnés sur la branche servie (`git ls-remote --symref
  origin HEAD`, puis `git log --oneline origin/main -30`) ; contrats du §4.1 en `locked`
  (`jq -r '.contracts[] | "\(.contract) \(.status)"' vendor/contracts/pin.json`, format
  `signalement.contract-pin.v2`) ; `packages/domain/delivery-envelope.ts` présent. Sinon :
  ne pas démarrer, rendre `BLOCKED` avec la commande qui l'a montré.
- **Worktree.** L7 tourne en parallèle de L6 : worktree créé sous un chemin `mktemp -d`,
  retiré par `git worktree remove` dans le même flux, échec compris. Branche :
  `git switch -c feat/v1-l7-cli` depuis la tête servie.
- **Registre §4.7 tel quel.** Cinq commandes exactement :

```
signalement submit <export.zip> (--origin <origin> | --no-origin) [--server <url>]
signalement status <dossier-id> [--server <url>]
signalement receipt <receipt-id> [--server <url>]
signalement keys [--server <url>]
signalement verify-receipt <receipt.json> --keys <keys.json> [--export <export.zip>]
```

  Jeton lu **uniquement** dans `SIGNALEMENT_TOKEN` (pas d'option `--token` : elle irait
  dans l'historique du shell et dans `ps`). Serveur : `--server`, sinon
  `SIGNALEMENT_SERVER`. Codes de sortie : `0` vérifié ou accepté, `1` refusé ou invalide
  (échec de transport compris), `2` usage. Sortie : un document JSON sur stdout terminé
  par `\n` ; exception : en succès, `receipt` et `keys` écrivent les octets JCS exacts,
  sans saut de ligne final, pour que `signalement receipt <id> > r.json` produise le
  fichier attendu par `verify-receipt`. stderr reste vide sur tout chemin géré.
  `verify-receipt` ne lit ni jeton ni serveur et ne touche jamais le réseau.
- **Noms du registre, importés tels quels.**
  - L1 : `DeliveryEnvelope`, `buildDeliveryEnvelope(exportBytes, observedOrigin):
    Promise<DeliveryEnvelope>` (`packages/domain/delivery-envelope.ts`), champs
    `deliveryId`, `exportSha256`, `exportByteLength`, `observedOrigin` ; vérificateurs
    `rawDeliveryEnvelopeFailures`, `rawProjectionReceiptFailures`,
    `rawSigningKeySetFailures`, chemins résolus par
    `jq -r '.files | keys[]' vendor/contracts/pin.json | grep quality/` ; corpus
    `contracts/fixtures/signalement-projection-receipt-v1/signature-vectors.v1.json`
    (vendorisé) ; `parsePin` (`tools/contracts/pin.ts`).
  - L2 : `loadPolicyReceipt`, `PolicyReceiptApi` (`verifyReceipt` ; `signReceipt` dans
    les tests seulement, `keyId` lu dans `unsigned.keyId`, clé secrète = graine Ed25519
    de 32 octets), `ProjectionReceipt`, `UnsignedReceipt`, `ReceiptVerification`
    (`signature: "valid" | "invalid" | "unknown-key" | "unreadable"`, `keyId: string |
    null`, `keyStatus: "active" | "retired" | null`), `PublicKeySet` (`{ organization;
    keys: { keyId; algorithm: "ed25519"; publicKey; status; notBefore; notAfter }[] }`),
    `WithholdReason`, `PolicyReceiptError`.
  - L3 : `Result`, `ProjectionState`, `projectionId`, `markerText`, `renderBody`,
    `RenderInput`, `RenderedBody`, `RENDERER_VERSIONS`, `parseExportPayloadView`,
    `buildRenderInput`, `PlannedDestination`, `buildExportFixture`, `FakeProvider`.
  - L4 : routes du §4.5 ; `startTestControlPlane` et `TestControlPlane`
    (`apps/control-plane/testing/harness.ts`).
  - Point d'entrée supposé `packages/<nom>/index.ts` : ajuster au fichier livré, sans
    renommer un symbole.
- **Jeton.** Il n'apparaît dans aucune sortie, aucune erreur, aucun journal, aucun
  message d'exception. Il n'est transmis que dans l'en-tête `Authorization`, schéma
  `Bearer`, vers l'origine `--server` exacte. Le gate de frontière publique refuse le
  littéral d'un tel en-tête dans l'arbre suivi (`tools/ci/public-boundary.ts:65-67`) :
  les tests construisent le nom et le schéma par concaténation
  (`["Author", "ization"].join("")`), comme `tools/ci/check-public-boundary.test.ts:255`,
  et la même règle vaut pour une URL à identifiants, coupée autour de l'arobase
  (`"https://" + "u:p" + "@" + "host.example"`) : le gate refuse aussi un fragment de
  forme `user@host` (`personal-email`). Chaque fois avec un commentaire d'une ligne qui
  dit pourquoi.
- **Réponses du serveur = données.** La CLI n'imprime jamais `error.message` ni un texte
  libre de réponse ; seuls des champs validés (motif, énumération, URL `https:`
  reparsée) sont réémis. Un état inconnu, un champ manquant ou mal typé donne
  `response.invalid`, jamais une valeur devinée.
- **Échec fermé.** TLS invalide, redirection, corps de réponse au-delà de 1 048 576
  octets : refus. `http:` refusé sauf hôte de bouclage (Task 3).
- **Fichiers interdits dans l'arbre.** Aucun `.zip`, `.png`, clé privée, certificat ou
  jeton commité (`tools/ci/public-boundary.ts:44`, `:69-71`). Exports, certificats TLS
  et clés de test sont générés à l'exécution dans un `mktemp -d` retiré en `finally`.
  Aucun répertoire `data/` ni `exports/` (`tools/ci/public-boundary.ts:47`).
- **Pas de seconde implémentation.** Borne : `MAX_ARCHIVE` (`packages/domain/zip.ts:6`) ;
  export : `tools/contracts/verify-export.ts` ; JSON strict : `parseStrictJson`
  (`vendor/contracts/tools/quality/policy-core-raw-inputs.ts:233`) ; JCS :
  `canonicalJson` (`vendor/contracts/tools/quality/authorized-execution.ts:1087`) ;
  enveloppe : L1 ; rendu : L3.
- **Faits volatils** (sha, version de Bun, numéros) : dérivés par les commandes
  ci-dessus, jamais recopiés. Les valeurs fixées par le registre (codes de sortie,
  libellés, motifs) sont des invariants.
- **Commits.** `bun run check` vert avant et après ; `git commit -s` (sign-off en
  dernière ligne, identité de la config git), message anglais, aucun trailer
  `Co-Authored-By`. Chaque test ajouté est prouvé par neutralisation (substitution
  no-op) ; le corps du commit cite la neutralisation et répond aux deux questions de
  `gate-integrity` §5.

## Review Focus

1. **TOCTOU entre vérification et envoi** : export modifié sur disque après la lecture.
   Test `submit sends exactly the verified bytes, never a second read` (Task 5).
2. **`NODE_TLS_REJECT_UNAUTHORIZED=0` hérité** de l'environnement. Test
   `TLS stays strict when NODE_TLS_REJECT_UNAUTHORIZED=0` (Task 4).
3. **Redirection qui emporterait le jeton** vers une autre origine. Test
   `a redirect is refused and the redirect target receives no request` (Task 4).
4. **Séquences de contrôle de terminal** dans un champ de réponse (`\u001b`, C1
   `\u009b`) : `JSON.stringify` échappe C0, pas C1. Tests
   `status never re-emits control characters from the server` (Task 6) et
   `server error codes outside the code pattern become server.error` (Task 4).
5. **Reçu téléchargé altéré ou non canonique** : `receipt` écrirait sur disque des octets
   que `verify-receipt` rejetterait plus tard sans dire pourquoi. Test
   `receipt refuses bytes that are not exactly JCS` (Task 7).
